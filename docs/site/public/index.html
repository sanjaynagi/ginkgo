AI-native scientific workflows, plain Python.

Ginkgo runs scientific workflows in plain Python. Each task is a function. Ginkgo links the tasks into a dynamic graph, running independent tasks in parallel and skipping work that's been done before. Built from the ground up to be written, executed and inspected by AI agents.

How a workflow grows

A flow plans the work. Calling tasks builds a graph. Ginkgo checks the planned graph before anything runs.

The graph grows as it runs. A task can look at its inputs and add new tasks. The work then follows the data.

Three founding principles

Plain Python

You write workflows as ordinary Python functions, with no separate workflow language to learn.

Graphs that grow

A task can look at its inputs and add new tasks. The workflow takes the shape the data needs.

Built for agents

AI agents can write, run and inspect workflows as well as people can, through plain Python, JSON output and a queryable record of every run.

Plain Python, from the first task to the last

You don't need to learn a workflow language. Tasks are decorated functions, and a flow is a function that calls them. 

from ginkgo import file, flow, shell, task

samples = ["S01", "S02", "S03"]


@task(kind="shell", env="seqkit")
def clean(sample: str, assembly: file) -> file:
    out = f"results/{sample}.fasta"
    cmd = f"seqkit seq -m 200 {assembly} -o {out}"
    return shell(cmd=cmd, output=out)


@task()
def count_contigs(assemblies: list[file]) -> dict[str, int]:
    return {str(a): open(a).read().count(">") for a in assemblies}


@flow
def main():
    paths = [f"data/{s}.fasta" for s in samples]
    cleaned = clean().map(sample=samples, assembly=paths)
    return count_contigs(assemblies=cleaned)
  • Calling a task inside a flow returns a node in the graph, not a result. Ginkgo builds and checks the planned graph before anything runs.
  • .map() runs the task once for each sample, and the runs go in parallel.
  • env="seqkit" runs the command in its own Pixi environment, which Ginkgo installs the first time it's needed.
  • Run the flow again and a task reruns only if its code, inputs or environment changed.

What Ginkgo takes care of

Caching by content

Ginkgo saves each result under the task's code, inputs and environment. Change one task and it runs again. Tasks after it run again only if its output changed.

An environment per task

Shell tasks run in their own Pixi environment or container image, named on the task.

Provenance you can query

Ginkgo records every run. You can ask which task made a file or why a task ran again, or query the record with SQL.

Your laptop, then a cluster

Workflows run locally by default. With an executor plugin, the same flow can send tasks to Kubernetes or GCP Batch.
